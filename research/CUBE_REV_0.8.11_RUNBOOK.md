## Checkpoint F — journal invariants

Verify the following journal transitions:

```text
PREPARED
  → TARGET_WRITTEN
  → ARCHIVE_WRITTEN
  → FENCE_WRITTEN
  → COMMITTED
```

Only these terminal alternatives are valid:

```text
ROLLED_BACK
ROLLED_BACK_TO_LEGACY
```

Every journal mutation must carry:

- `transaction_epoch`;
- `last_writer_epoch`;
- `last_writer_owner`;
- source identity and exact raw source;
- target storage key;
- archive key;
- phase timestamp.

The active owner record must match before and after every fenced mutation.

## Checkpoint G — authority and divergence cases

### Before `FENCE_WRITTEN`

- A source mutation invalidates the attempted migration.
- Do not adopt the target.
- Remove the target when it is safe to do so.
- Record rollback or quarantine evidence.
- Re-enter source selection only from a terminal rollback state.

### At or after `FENCE_WRITTEN`

- The target is authoritative if currently valid and identity-compatible with the journal.
- A source mutation is downgrade mutation.
- Quarantine the mutated source evidence.
- Do not replace the valid target with the lower-version state.

### After `COMMITTED`

Do not require the target's current integrity to equal its initial target integrity. Valid telemetry and responses legitimately change it. Require instead:

- current 0.8.11 schema and integrity validity;
- current verified asset binding;
- matching `upgrade_epoch`;
- matching migration source key and source integrity in provenance;
- matching session identity.

## Checkpoint H — source ancestry

When a valid 0.8.10 source coexists with a preserved 0.8.8 or 0.8.9 source, accept the higher source only when:

- participant token, session ID, sequence, and schedule agree;
- lower responses are an exact common prefix;
- lower cursor does not exceed higher cursor;
- the 0.8.10 migration provenance names that lower source key and integrity.

Otherwise return `ANCESTRY_CONFLICT` and quarantine evidence. Do not choose by version number alone.

## Checkpoint I — crash positions

Inject and recover each phase independently:

```text
PREPARED
TARGET_WRITTEN
ARCHIVE_WRITTEN
FENCE_WRITTEN
COMMITTED
```

Expected convergence:

- crash after `PREPARED`: rollback/reselection or recovery of a matching orphan target;
- crash after `TARGET_WRITTEN`: validate source and target, then continue archive/fence/commit;
- crash after `ARCHIVE_WRITTEN`: validate target, source, and archive, then fence;
- crash after `FENCE_WRITTEN`: preserve target authority and finish commit;
- crash after `COMMITTED`: resume the target even after legitimate later integrity changes.

No case may silently create a different token, session ID, sequence ID, schedule, or migration epoch.

## Checkpoint J — rollback cases

### Safe downgrade rollback

When the committed target is lost or invalid and:

```text
current source raw == journal source raw == exact archive raw
```

then:

- remove an invalid target if present;
- record `ROLLED_BACK_TO_LEGACY`;
- mark the fence as rolled back;
- return the original version route;
- do not rewrite the source.

### Unsafe rollback

When target loss and source divergence coexist:

- do not choose the target or source automatically;
- quarantine journal, source, archive, and target evidence;
- block the participant flow.

## Checkpoint L — actual browser smoke test

Serve over HTTP or HTTPS, not `file://`.

Use two real tabs or windows on the same origin and browser profile.

Test at minimum:

1. two tabs press start concurrently with no prior state;
2. two tabs enter concurrently with one unfinished 0.8.8 source;
3. one tab is paused while the other completes migration;
4. close the winning tab at each journal phase using an instrumented test build;
5. reload and verify deterministic convergence;
6. leave a legacy page open before migration, then write after the fence and reopen 0.8.11;
7. remove or corrupt the target while source/archive remain exact;
8. remove or corrupt the target after mutating the source;
9. confirm unsupported Web Locks environments fail closed without creating state;
10. verify sealed legacy states route to their original version.

Record browser name, exact version, OS, tab/window topology, local-storage evidence before and after, journal epoch, owner token, and resulting action.

## External stop gates

This version does not authorize:

- production default-entry cutover;
- live Collector POST and receipt claim;
- live Factory reconstruction claim;
- deletion of preserved legacy source or archive;
- fallback migration on browsers without Web Locks;
- claim that every active-session write is multi-tab safe.

## Known internal hold

The exclusive lock covers initialization, migration, reconciliation, rollback, and resume arbitration. It does not yet protect every later response, telemetry, post-task, snapshot, or submission write. Two already-active 0.8.11 tabs could still overwrite a newer local revision through ordinary runtime persistence.

That boundary belongs to CUBE-REV 0.8.12.

## Promotion rule

0.8.11 may remain an internally certified stacked research PR after checkpoints C–K pass. Production promotion requires an owner-observed native multi-window walkthrough and an explicit decision on the active-session write-concurrency hold.
